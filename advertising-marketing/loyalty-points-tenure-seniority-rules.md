# Loyalty points – Tenure (seniority) rules

## 1. Requirements & Compatibility

- **Supported PrestaShop Versions**: PrestaShop 1.7.x, 8.x, 9.x
- **PHP Compatibility**: PHP 7.1 - 8.5
- **Hosting Requirements**: Standard PHP extensions (cURL, JSON, OpenSSL) are typically required for PrestaShop itself and are usually available on most hosting environments. This module does not have additional specific requirements beyond a standard PrestaShop setup.

## 2. Complete Configuration Walkthrough (Every Setting Grouped by Screen)

### 2.1 Module Configuration Page (Back Office > Modules > Configure)

This is the main configuration screen for the module, accessed immediately after installation or by clicking “Configure” from the Module Manager.

**General Settings**

- **Enable Module:**

  - **What this setting does:** This is the master switch to activate or deactivate the entire module’s functionality.
  - **Effect of changing this setting:**
    - *When enabled:* The module will start processing loyalty rules based on customer tenure and awarding points as configured.
    - *When disabled:* The module will cease to function. No new points will be awarded based on seniority rules, and existing rules will be ignored until re-enabled.
  - **Recommended value:** YES
  - **Merchant scenario / example:** You’ve finished setting up your rules and are ready to launch your loyalty program. Enable this to start rewarding customers. If you need to temporarily pause the program for maintenance or review, you can disable it here.
- **Cron Job URL:**

  - **What this setting does:** This displays a unique URL that you need to set up as a “cron job” on your web server. A cron job is a scheduled task that tells your server to run this URL automatically at regular intervals (e.g., once a day). This is how the module checks customer seniority and awards points without you having to manually trigger it.
  - **Effect of changing this setting:** You cannot change this URL directly. It’s generated by the module.
    - *When correctly configured as a cron job:* The module will automatically run its checks and award points according to your rules.
    - *When NOT configured as a cron job:* The module’s automatic point awarding will not occur. You would have to manually visit this URL in your browser to trigger the process, which defeats the purpose of automation.
  - **Recommended value:** Copy this URL and set it up as a daily cron job on your server.
  - **Merchant scenario / example:** After installing the module, copy this URL. Go to your hosting control panel (e.g., cPanel, Plesk) and find the “Cron Jobs” or “Scheduled Tasks” section. Add a new cron job to execute this URL once every 24 hours. This ensures your customers receive their seniority points automatically and on time.

### 2.2 Dedicated Admin Screen: Loyalty Tenure Rules (Back Office > MyPresta.eu > Loyalty Tenure Rules)

This screen allows you to define and manage the specific rules for awarding loyalty points based on customer seniority.

- **Screen Name & Menu Location:** You can find this screen by navigating to **MyPresta.eu > Loyalty Tenure Rules** in your PrestaShop Back Office menu.
- **Available Actions & Settings:**

  - **Rule Listing Table:** This table displays all your active and inactive seniority rules. For each rule, you’ll see:
    - **ID:** A unique identifier for the rule.
    - **Tenure (Days):** The minimum number of days a customer must have been registered to qualify for this rule.
    - **Points to Award:** The number of loyalty points a customer will receive.
    - **Active:** A switch to enable or disable the rule.
    - **Actions:** Buttons to “Edit” or “Delete” a rule.
  - **“Add New Rule” Button:** Click this button to create a new seniority rule.

  **When Adding/Editing a Rule:**
  You will be presented with a form to define the rule’s parameters:

  - **Tenure (Days):**

    - **What this setting does:** This is the minimum number of days a customer must have been registered on your store to be eligible for this specific loyalty point award.
    - **Effect of changing this setting:**
      - *Setting to 365:* Customers registered for at least one year will qualify.
      - *Setting to 730:* Customers registered for at least two years will qualify.
    - **Recommended value:** Choose values that represent meaningful milestones for your customers (e.g., 365 days for 1 year, 730 days for 2 years, 1095 days for 3 years).
    - **Merchant scenario / example:** You want to reward customers who have been with your store for at least one year. You would set this to `365`.
  - **Points to Award:**

    - **What this setting does:** This is the exact number of loyalty points that will be granted to a customer who meets the “Tenure (Days)” requirement for this rule.
    - **Effect of changing this setting:**
      - *Setting to 100:* Qualifying customers receive 100 loyalty points.
      - *Setting to 50:* Qualifying customers receive 50 loyalty points.
    - **Recommended value:** Align this with the value of your existing loyalty points program. A good starting point might be points equivalent to a small discount (e.g., 5-10% of an average order value).
    - **Merchant scenario / example:** To give a significant thank you for one year of loyalty, you might award `250` points, which could translate to a €5 discount on their next purchase.
  - **Active:**

    - **What this setting does:** This switch determines whether this specific rule is currently active and will be considered by the module when awarding points.
    - **Effect of changing this setting:**
      - *When enabled:* The rule will be processed by the cron job, and points will be awarded to qualifying customers.
      - *When disabled:* The rule will be ignored, and no points will be awarded based on this specific seniority threshold.
    - **Recommended value:** YES (for rules you want to be active).
    - **Merchant scenario / example:** You’ve created a rule for 5 years of seniority but want to test it internally before making it live. You can keep it disabled until you’re ready to activate it.
- **Effect of changes:**

  - Adding a new rule creates a new entry in the database that the module’s cron job will check against.
  - Editing a rule modifies its parameters (tenure, points, active status), affecting future point awards.
  - Deleting a rule permanently removes it, and no further points will be awarded based on that specific seniority.
  - The `PS_LIST_LIMIT` configuration key controls the number of items displayed per page in the rule listing table.
- **Recommended workflow for daily store management:**

  1. **Plan your loyalty tiers:** Decide what seniority milestones you want to reward (e.g., 1 year, 2 years, 5 years).
  2. **Calculate point values:** Determine how many points you want to award for each tier, considering the monetary value of your loyalty points.
  3. **Create rules:** Go to **MyPresta.eu > Loyalty Tenure Rules** and click “Add New Rule” for each tier.
  4. **Monitor:** Periodically check your customer loyalty point balances and ensure the cron job is running correctly.

## 5. Merchant Troubleshooting & Frequently Asked Questions (FAQ)

**Q1: My customers aren’t receiving loyalty points, even though I’ve set up rules.**
A1:

- **Check Module Activation:** Ensure the “Enable Module” setting on the main configuration page is set to YES.
- **Verify Cron Job:** The most common reason is an incorrectly set up or non-running cron job. Double-check the Cron Job URL from the module’s configuration page and ensure it’s correctly configured on your hosting server to run daily.
- **Rule Status:** Make sure the individual loyalty tenure rules you’ve created are marked as “Active.”
- **Customer Eligibility:** Has the customer actually met the “Tenure (Days)” requirement for any of your active rules? The module only awards points once a customer crosses a threshold.
- **Smarty Cache:** Sometimes, PrestaShop’s cache can cause display issues. Go to **Advanced Parameters > Performance** and click “Clear cache” (or “Clear Smarty cache” in older versions).

**Q2: How do I know if the cron job is running correctly?**
A2:

- **Check Hosting Logs:** Most hosting providers offer a way to view cron job execution logs in your control panel (e.g., cPanel). Look for entries related to the cron job URL provided by the module.
- **Manual Test:** You can manually visit the Cron Job URL in your web browser. This will trigger the point awarding process for that moment. If points are awarded to eligible customers after this manual visit, it confirms the module logic is working, and the issue is with the automated cron setup.

**Q3: Can I award points retroactively to customers who already passed a seniority milestone before I installed the module?**
A3: Yes, when the cron job runs for the first time after you’ve set up rules, it will evaluate all existing customers against your active rules. If a customer meets a tenure requirement and hasn’t been awarded points for that specific rule before, they will receive them. This means older, loyal customers will get their deserved points.

**Q4: My custom theme doesn’t show loyalty points correctly, or the notifications look off.**
A4: This module primarily interacts with PrestaShop’s core loyalty system. Any display issues with loyalty points or notifications are usually related to your theme’s styling or overrides for the native loyalty module.

- **Theme Customization:** If you have a custom theme, it might have its own templates or CSS for displaying loyalty information. You may need to consult your theme developer or a webmaster to ensure it correctly integrates with PrestaShop’s loyalty features.
- **Default Theme Test:** Temporarily switch to the default PrestaShop theme (Classic) to see if the issue persists. If it works correctly on the default theme, the problem is definitely with your custom theme.

**Q5: What happens if I change a rule (e.g., increase points) after customers have already received points from it?**
A5: The module is designed to award points *once* for each rule when a customer first meets the tenure threshold. If you change a rule (e.g., increase points for 365 days from 100 to 150), customers who already received 100 points for 365 days will *not* automatically receive the additional 50 points. The rule has already been “satisfied” for them. If you want to give them the extra points, you would need to manually adjust their loyalty balance or create a new, temporary rule.

## 6. Developer & Webmaster Guide (Technical Architecture & Code Map)

### 6.1 Architecture Overview

The “Loyalty points – Tenure (seniority) rules” module (`myprestaloyalty_tenure`) extends PrestaShop’s functionality by introducing a new concept of loyalty point awards based on customer registration tenure. It follows a standard PrestaShop module architecture, leveraging `ObjectModel` for managing seniority rules and a dedicated front controller for cron job execution. The module integrates with the core PrestaShop `LoyaltyModule` to award points, ensuring compatibility with the native loyalty system.

### 6.2 Controllers (`controllers/`)

- **Front-Office Controllers**:

  - `controllers/front/cron.php`
    - **Class Name:** `MyprestaloyaltyTenureCronModuleFrontController` (extends `ModuleFrontController`)
    - **Responsibility:** This controller is designed to be executed via a cron job. When accessed, it iterates through all active tenure rules and all registered customers. For each customer, it calculates their registration age and checks if they qualify for any active rule for which they haven’t yet received points. If a customer qualifies, it awards the specified loyalty points using the core `LoyaltyModule` functionality. It typically returns a simple success message or log output.
  - `controllers/front/index.php`
    - **Class Name:** `MyprestaloyaltyTenureIndexModuleFrontController` (extends `ModuleFrontController`)
    - **Responsibility:** This is a placeholder or default front controller. In many modules, if no specific action is defined, `index.php` might handle a default view or redirect. For this module, its primary front-office interaction is via the `cron.php` controller.
- **Back-Office Admin Controllers**:

  - `controllers/admin/AdminMyprestaloyaltyTenureController.php`
    - **Class Name:** `AdminMyprestaloyaltyTenureController` (extends `ModuleAdminController`)
    - **Tab Name:** “Loyalty Tenure Rules” (under MyPresta.eu menu)
    - **Managed Entity:** `MyprestaloyaltyTenureRule` (maps to `_myprestaloyalty_tenure_rule` database table)
    - **Responsibility:** This controller provides the CRUD (Create, Read, Update, Delete) interface for managing loyalty tenure rules in the PrestaShop Back Office. It uses `HelperList` for displaying the list of rules and `HelperForm` for adding/editing individual rules. It handles form submissions, validation, and interaction with the `MyprestaloyaltyTenureRule` `ObjectModel`.
  - `controllers/admin/index.php`
    - **Class Name:** (No specific class, typically used for security)
    - **Responsibility:** This file usually contains a simple `header('Location: ../../index.php?controller=AdminHome'); exit;` or similar to prevent direct directory listing and ensure that admin controllers are accessed through the PrestaShop dispatcher.

### 6.3 Core Classes & Models (`classes/`)

- `classes/index.php`

  - **Responsibility:** Standard PrestaShop security file, typically containing `header('Location: ../../index.php?controller=AdminHome'); exit;` to prevent direct access to the `classes` directory.
- `classes/MyprestaloyaltyTenureRule.php`

  - **Class Name:** `MyprestaloyaltyTenureRule` (extends `ObjectModel`)
  - **Database Table:** `_myprestaloyalty_tenure_rule`
  - **`$definition` fields:**
    - `id_myprestaloyalty_tenure_rule`: Primary key.
    - `tenure_days`: Integer, the minimum number of days a customer must be registered.
    - `points_to_award`: Integer, the number of loyalty points to grant.
    - `active`: Boolean, whether the rule is active (0 or 1).
  - **Key Public Methods:**
    - `__construct()`: Standard `ObjectModel` constructor.
    - `add()`: Overrides `ObjectModel::add()` for custom logic if needed (e.g., date handling, validation).
    - `update()`: Overrides `ObjectModel::update()`.
    - `delete()`: Overrides `ObjectModel::delete()`.
    - `getAllActiveRules()`: Static method to retrieve all active rules from the database.
    - `hasCustomerReceivedPointsForRule($id_customer, $id_rule)`: Static method to check if a specific customer has already been awarded points for a given rule. This is crucial to prevent duplicate awards.
    - `markCustomerAsAwarded($id_customer, $id_rule)`: Static method to record that a customer has received points for a rule.

### 6.7 Database Schema & Hooks Map

- **Database Tables**:

  - `ps_myprestaloyalty_tenure_rule`: Stores the definitions of each seniority rule.
    - `id_myprestaloyalty_tenure_rule` INT(10) UNSIGNED NOT NULL AUTO\_INCREMENT
    - `tenure_days` INT(10) UNSIGNED NOT NULL
    - `points_to_award` INT(10) UNSIGNED NOT NULL
    - `active` TINYINT(1) UNSIGNED NOT NULL DEFAULT ‘1’
    - PRIMARY KEY (`id_myprestaloyalty_tenure_rule`)
  - `ps_myprestaloyalty_tenure_awarded`: Records which customers have received points for which rules, to prevent duplicate awards.
    - `id_myprestaloyalty_tenure_awarded` INT(10) UNSIGNED NOT NULL AUTO\_INCREMENT
    - `id_customer` INT(10) UNSIGNED NOT NULL
    - `id_myprestaloyalty_tenure_rule` INT(10) UNSIGNED NOT NULL
    - `date_awarded` DATETIME NOT NULL
    - PRIMARY KEY (`id_myprestaloyalty_tenure_awarded`)
    - UNIQUE KEY `customer_rule` (`id_customer`, `id_myprestaloyalty_tenure_rule`)
- **Registered Hooks Table**:
  The module does not explicitly register any front-office display hooks (like `displayHeader`, `displayRightColumn`, `displayProductExtraContent`, `displayFooter`) as its primary function is background processing via cron.
  It implicitly uses:

  | Hook Name | Execution Timing | Technical Purpose |
  | --- | --- | --- |
  | `actionModuleInstall` | During module installation | Creates database tables, registers admin tab. |
  | `actionModuleUninstall` | During module uninstallation | Deletes database tables and configuration. |
  | `actionAdminControllerSetMedia` | When an admin controller is loaded | If the module had custom JS/CSS for admin, it would register it here. (Not used in this module based on inventory) |
  | `displayBackOfficeTop` | Renders content at the top of the Back Office | Used to display the cron job URL and instructions on the module’s configuration page. |
